# 平台 SKU 毛重初始化与增量更新

适用于用户提供快递账单 Excel 路径或目录，要求建立或更新平台 SKU 的“商品＋包装”重量估计。平台 SKU ID 是唯一业务标识；重量来源是快递账单的计费重量，属于统计代理，不是实测物理重量。此流程不修改旺店通，也不自动改变利润计算政策。

## 输入与模式

- 首次建立：`tbcli profit sku-gross-weight init --input '<FILE.xlsx|DIR>' --shop-key '<KEY>' [--year '<YYYY>'] --json`。
- 已初始化后新增账单：`tbcli profit sku-gross-weight update --input '<FILE.xlsx|DIR>' --shop-key '<KEY>' [--year '<YYYY>'] --json`。
- 单文件名称不能明确识别承运商和账月时，可显式提供 `--carrier sto|yunda|jt|sf --bill-month YYYY-MM`。目录逐文件识别；文件名缺年份时，使用同目录可确认的唯一年份或显式 `--year`，不猜测跨年账单。
- 人工补充：`tbcli profit sku-gross-weight manual-import --input '<WEIGHTS.json>' --shop-key '<KEY>' --json`。JSON 含 `source:{name,uri,revision}` 与 `weights:[{platformSkuId,platformProductId,estimateKg,sourceRow}]`；只接收正数 kg，SKU ID 保持文本，来源行号用于回查。
- 需要数据库维护权限与用户对本次入库的明确授权。用户只要求试算或核对时，不执行这两个写命令。

## 主流程

1. 检查 `tbcli --version`、`tbcli capabilities --json`、`tbcli db access-check --json`，精确识别输入路径中的文件、承运商和账月。先校验所有账单；任何一份不合格时，整批停在写入前。
2. 执行对应命令。CLI 对已导入账单保持幂等；对新账单调用现有快递账单导入能力。校验并导入后的来源批次用于限定本次运单范围。
3. CLI 匹配唯一订单运单和一致的正计费重量，按当前平台 SKU→ERP 子件映射核对订单子件数量，还原购买件数。单平台 SKU 且恰好购买一件的包裹写入 `mart.platform_sku_gross_weight_samples`，作为直接估算证据。
4. 读取历史有效单件重量，计算核密度主峰和 0–1 置信评分，写入 `master.current_platform_sku_gross_weights`，状态为 `estimated`。一个有效样本也给出重量，样本量少则评分上限较低。
5. 多平台 SKU 包裹保存到 `mart.platform_sku_gross_weight_multi_packages`。先核对每个 SKU 的子件映射与购买件数，再从账单重量中扣除已知 SKU 的净货重和一次共享外包装 0.2 kg。恰好一个 SKU 未知时，剩余重量归给它：两件 SKU 的账单重量 1.3 kg、已知 SKU 毛重 0.7 kg，则另一 SKU 的候选毛重为 `1.3-0.7+0.2=0.8 kg`。多个 SKU 同时未知时，把剩余净货重按其购买件数均分，再给每个单位加 0.2 kg，作为暂定毛重。此时单张包裹账单不能唯一识别各 SKU 的真实重量，故候选来源记为 `shared_unknown_residual`，当前估计置信评分上限 0.1；恰好一个未知的推算评分上限 0.55。
6. 逐包候选值、未知 SKU 数、已知锚点和来源批次保存在 `mart.platform_sku_gross_weight_residual_samples`。同一 SKU 有单未知候选时优先用它统计毛重；仅在没有单未知候选时使用多未知均分候选。直接单 SKU 估计始终高于两种推算，且推算值不能作为下一级推算的锚点。异常、映射不符或非正剩余净重不采用。
7. 核对命令返回的账单批次、单 SKU 样本、多 SKU 包裹、两类剩余重量候选、推算 SKU、变化样本和当前表总量。相同输入再次运行应不重复增加样本或估计版本。后续出现更高优先级的证据时，重新更新当前毛重。

## 人工毛重的使用与替换

当用户提供经人工填写的 SKU 毛重清单时，先核对 SKU ID 唯一、单位为 kg、重量为正数和来源行号，然后调用 `manual-import`。入库状态为 `manual-estimate`，方法为 `platform-sku-gross-manual-v1`，置信评分固定 0.05、级别 `low`，快递有效样本数为 0。该值参与利润运费分摊，报告仍以低置信度提示。零值表示未估算，不能当作有效毛重入库。

已有正数的快递直接估计或多 SKU 推算保持优先；人工值不会覆盖它们。普通增量更新不会用多 SKU 剩余重量推算覆盖人工值。后续快递账单出现该 SKU 的有效单 SKU、单购买件数订单时，`update` 会用直接样本重新估算并自动替换人工值；版本历史保留先前人工值、来源和替换批次。核对命令输出的导入数、未变数、跳过已有快递估计数与写后行数，再继续利润计算。

## 增量与修订边界

- 更新命令只从本次账单批次识别运单并复核对应订单，不重新读取所有历史快递订单。历史单 SKU 样本和多 SKU 包裹摘要保留在仓库；统计估计读取历史证据并随新的直接重量锚点更新。仅保存样本数、均值不足以重算主峰、置信区间和尾部比例。
- 逐包样本以店铺键、旺店通订单号和运单号去重；来源批次、子件数量和核对状态随样本保存。来源重量或组合映射变化时，应让受影响包裹重新核对，而不是把更正作为新包裹叠加。重算后失效的剩余重量候选标记为非活跃，若某 SKU 没有其他有效证据，则撤销当前推算重量。
- 当前估计与版本历史分别存储；`meta.platform_sku_gross_weight_runs` 记录本次范围和写后数量。该版本历史是重量依据的审计轨迹，不是利润计算快照。
- 评分反映样本证据支持度，不是“真实物理重量正确”的概率。计费重量集中在 1kg 的轻件可能受快递计费规则影响；在物理重量审计前，不据此认定快递公司多收费。

## QA 与失败

- 未初始化却调用 `update`、已初始化却调用 `init`、来源账单有冲突、订单与运单关系不唯一、组合关系缺失或不一致、写后行数不符时，返回明确状态。组合关系缺口只影响相应 SKU，不把整包重量冒充单件重量。
- 账单导入与重量更新是两个受控阶段；如果账单已入库但重量事务失败，重试同一命令会复用既有账单批次并继续完成重量更新。
- 只在当前受支持的操作系统和 Agent 上声称已实际测试；其他目标通过相同 npm CLI/Skill 契约分发，但未执行环境不得声称已验证。

# 月度实际利润口径

本页定义取得月度订单、退款观察窗和实际快递账单后运行的经营利润。它服务经营分析，不替代法定财务报表、税务申报或平台结算时间口径的财务利润表。

## I → S → O

### Input

- 一个可由 `profit orders identity` 发现的稳定店铺键；员工不需要记忆底层编号。
- 一个完整自然月，最终解析为月初、月末、业务时区和退款观察截止时间。
- 默认使用 `operating-profit-v5`：订单头实付为收入总额，平台费率6%、税率2%、未匹配运单每单估算运费2元；商品子件成本取当前已批准的 SKU 成本主数据，订单内物流费按平台 SKU 毛重分摊。未发货仅退款冲回对应商品的全部成本并从发货重量中扣除；退货退款按可二次销售比例暂估冲回成本，默认比例为 50%，可用 `--return-resale-rate` 设置 0～1。`operating-profit-v4` 保留原退款成本口径，`v3` 保留收入占比运费分摊，`v2` 与 `v1` 也可显式复核。
- 可选负责人范围，以及 `shop|owner|product|day|report` 汇总粒度；`report` 一次返回全店、负责人和商品三级数据，供分析报告使用。
- 数据缺失时只使用政策版本中已经批准的回退；没有批准回退的值保持 `missing`。

### Strategy

1. 收入订单按支付时间归属利润月，只纳入政策版本允许的有效状态。`operating-profit-v5`、`v4` 和 `v3` 将零实付、仅含 ERP 规格 `dc99999` 且全部明细销售额与源成本均为零的旺店通占位订单整体排除；该订单的运单及运费也不进入利润。若订单含其他规格或任一相关金额不为零，则保留订单并按正常质量规则核对。
2. 订单头收入来自 `raw.wdt_order_headers.paid_amount`（旺店通订单 `paid`），作为正式收入总额。商品明细优先取 `raw.wdt_order_lines.source_share_amount`（明细 `shareAmount`），缺失时取 `source_line_paid`（明细 `paid`），仅作为每个订单内部的分配权重；按订单头实付归一化后分到商品行。报告披露归一化前的原始差额。
3. 对利润月订单观察至次月15日23:59:59；只扣除截止前财务结算成功且实际退款金额大于零的退款。
4. 退款必须回挂原订单和商品明细。零候选、多候选与无法归属保留质量状态，不按名称、金额相近或行序猜测。
5. `operating-profit-v5` 先以 `master.current_sku_costs.unit_cost × raw.wdt_order_lines.quantity` 取得原销售商品成本，再减去未发货仅退款数量的全额成本和退货退款数量的可二次销售比例成本。`v4`、`v3` 与 `v2` 保留原销售数量全额成本口径。成本主数据按店铺键和 ERP 规格编码匹配当前已批准且可用的正成本，定期从旺店通系统规格 `refCostPrice` 同步。缺失、零值或无法唯一确认的成本逐项列出。已确认的非商品项目记为 `explicit_zero`。
6. 物流先按订单运单精确匹配快递账单，汇总同一运单的所有签名费用。未匹配账单的运单按每单2元估算；报告分别披露实际运费、估算运单数、估算运费和两者合计。
7. 订单物流总额已确定后再分到商品行。`v5` 使用扣除未发货退款数量后的平台 SKU 毛重与发货数量比例；组合装的子件数量须回勾。`v4` 保留原销售数量的毛重分摊，`v3` 按订单内归一化收入占比分摊。分摊方法均保持订单和全店物流总成本不变。
8. 推广费按店铺、利润月、转化周期、商品主体与平台商品 ID 汇总。只有 SKU 分析需要在商品内部继续分摊。
9. `operating-profit-v1` 按商品行净销售额计算平台费6%和税费2%。
10. 负责人按店铺、平台商品 ID 与政策规定的利润时点读取有效且已批准的版本；未分配、已下架和无法归属项保留并参与店铺总计。商品 `641773251256` 是补差价链接，负责人非必填，成本状态固定为 `explicit_zero`。商品 `2821074747423457561`、`2825068038544425323`、`2825699043848487166`、`2830808569970950560` 已确认为下架商品，负责人非必填，但继续使用各自实际商品成本。以上项目不进入负责人待确认缺口。
11. 返回每个金额的取值状态、成本来源与最近同步批次、占位订单排除数，以及店铺级回勾结果。当前成本会用于重新估值既往月份，报告注明运行时成本批次和政策版本。

### Output

- JSON 查询结果：店铺、利润月、退款截止、政策版本、运行状态、分组、金额拆分、利润率、来源状态和质量摘要；无法归属退款包含退款单号、旺店通订单号、平台订单号和明细标识。
- Excel：摘要、负责人汇总、商品汇总、SKU汇总、订单商品明细、退款回挂、物流对账、数据质量、计算规则。
- 数据缺口清单由独立 coverage 路线产生；计算结果只引用其状态，不把缺失值静默改成零。

## 平台 SKU 毛重运费分摊口径

先按运单匹配快递账单并确定订单运费。毛重只作为订单内各平台 SKU 的运费比例权重，不改写账单金额。毛重来自基于快递计费重量统计估算的 `master.current_platform_sku_gross_weights`，是商品加包装的代理值，不是实测净重。

1. 按 `shop_key + platform_sku_id` 读取状态为 `estimated`（单 SKU 包裹直接估算）或 `inferred`（多 SKU 包裹剩余重量估算）、样本数大于零且毛重大于零的当前估计。证据优先级为单 SKU 直接估算、单未知 SKU 剩余重量推算、多未知 SKU 剩余净重均分。后者属于很低置信度的暂定代理值，仍参与分摊并在质量摘要中标记。每次计算记录最近一次改变估计的重量运行批次。
2. 从 `master.current_platform_sku_components` 读取一件平台 SKU 对应的 ERP 子件编码及数量。将同订单、同平台 SKU、同 ERP 规格的订单子件数量相加；只有订单子件集合完整、数量与映射一致且各子件推出同一个正整数购买件数时，才确认该 SKU 的购买件数。组合装的毛重计一次再乘购买件数，不因展开为多条子件而重复计重。
3. `订单-SKU 分摊重量 = SKU 单位毛重 × 发货购买件数`；`订单-SKU 运费 = 订单运费 × 该 SKU 分摊重量 ÷ 订单全部有效 SKU 分摊重量`。`v5` 中同 SKU 展开的子件行按各自行的有效发货数量占比分配该 SKU 运费；商品与负责人汇总以平台商品 ID 归属。补差价等已确认非商品项目取零分摊重量。正负物流调整遵循同一比例，订单、商品、负责人和全店总额逐级回勾。
4. 有运单的订单若仍存在毛重缺失、组合映射不完整、子件数量不一致或无法得到正分摊总重量，`v5` 按有效发货数量加权的收入占比分摊订单运费；`coverage` 披露受影响订单、SKU 和回退运费金额，对应负责人和商品利润标记为 `provisional`。这一回退只改变订单内归属，不改变订单或全店运费与利润总额。旧口径复核可显式选择 `operating-profit-v3`。

该口径以跨负责人、组合装和三负责人订单为固定审计样例；金额分摊不得改变订单实际或估算运费合计。新增快递账单修正 SKU 毛重后，重新运行同一利润月份即可读取最新重量和成本主数据。

## 唯一公式

```text
商品行净销售额 = 商品行支付金额 - 截止日前实际结算退款

商品行平台费 = 商品行净销售额 × 政策平台费率
商品行税费 = 商品行净销售额 × 政策税率

商品行实际利润 = 商品行净销售额
                 - 商品成本
                 - 实际或政策允许的物流成本
                 - 商品推广费
                 - 商品行平台费
                 - 商品行税费
```

`v5` 以已财务结算的退款明细和原订单行 ID 或来源行 ID 关联。`未发货仅退款` 对应数量的成本全额冲回且不承担发货运费；`退货退款` 对应数量按人为设定的可二次销售比例暂估冲回成本，当前即使显示“待入库”也采用该暂估比例；`已发货仅退款` 与`退款不退货`保留原商品成本及发货运费。退款数量按原订单行销售数量封顶，无法映射的退款成本单独披露。报告同时列出原销售商品成本、未发货退款成本冲回、退货退款成本冲回及净商品成本。使用当前审核成本可重新估值既往月份；历史时点成本待有效日期和来源核实后由新政策切换。

## 取值状态

每个成本或费用项必须使用以下状态之一：

- `actual`：订单、退款、账单等直接事实。
- `standard/reference`：已批准的标准或参考主数据。
- `estimated`：政策允许的估算或回退。
- `explicit_zero`：业务事实确认金额为零，并保存原因；例如补差价链接 `641773251256` 的商品成本。
- `missing`：没有可用事实或批准回退；不得伪装为零。

报告至少披露各状态金额、对象数和对利润的影响。

## 运行状态

- `actual/reconciled`：订单、退款观察窗、实际物流、推广、政策和所需主数据均通过质量门，店铺级总额全部回勾。
- `provisional`：公式完整，但使用了批准的参考值或估算值；披露估算金额及占比。
- `incomplete`：存在没有批准回退的 `missing` 项；可以返回已知部分和缺口，但不能称为实际利润或已封账。

利润计算实时读取当前事实，不在数据库保存利润快照。每次计算后生成一份新的分析报告；报告记录月份、退款截止、政策版本、实际/估算金额和数据质量，补齐数据后生成新报告而不覆盖旧文件。

## 计算与缺口检查的边界

`profit actual query/export` 负责按本页方法计算或导出；`profit actual coverage` 只检查数据是否足以达到目标运行状态。coverage 不修改公式、政策、来源事实或利润结果。计算也不能因为 coverage 缺失而自动选择未经确认的回退方法。

## Required CLI contract

```bash
tbcli profit actual coverage --shop-key '<店铺键>' --month '<YYYY-MM>' [--policy-version '<版本>'] --json
tbcli profit actual query --shop-key '<店铺键>' --month '<YYYY-MM>' [--policy-version '<版本>'] [--return-resale-rate <0..1>] --group-by '<shop|owner|product|day|report>' [--owner '<姓名>' | --owners '<姓名1,姓名2>'] --json
tbcli profit actual export --shop-key '<店铺键>' --month '<YYYY-MM>' [--policy-version '<版本>'] [--owner '<姓名>' | --owners '<姓名1,姓名2>'] --out '<新文件.xlsx>' --json
tbcli profit actual audit-cost --shop-key '<店铺键>' --month '<YYYY-MM>' --product-id '<商品ID>' --json
tbcli profit actual audit-order-cost --shop-key '<店铺键>' --month '<YYYY-MM>' [--order-nos '<NO,...>' | --sample-size '<N>'] --json
tbcli profit actual audit-combo-cost --shop-key '<店铺键>' --month '<YYYY-MM>' [--product-id '<ID>'] [--platform-sku-id '<ID>'] --json
tbcli profit actual audit-reference-cost --shop-key '<店铺键>' --month '<YYYY-MM>' --json
tbcli profit actual audit-freight-fallback --shop-key '<店铺键>' --month '<YYYY-MM>' [--order-nos '<NO,...>'] [--limit 30] --json
```

`audit-cost` 是稳定只读的逐订单商品行成本一致性审计。它比较订单行 `goodsCost`、订单行 `refCostPrice × skuNum` 和支付日有效的已批准 SKU 成本版本 `unit_cost × skuNum`，不执行利润计算、不修改数据库，也不把某一套来源自动提升为正式成本政策。

`audit-order-cost` 是稳定只读的整单成本一致性审计。它把订单中的全部商品与 SKU 汇总到旺店通订单号，再比较三套成本总额；指定订单号时同时返回全部商品行的三套成本，稳定抽样时返回精简的订单汇总。抽样用于发现共性，不代替全量月度保证。

`audit-combo-cost` 识别同一订单内由同一商品与平台 SKU 展开的多个 ERP 子件，按组合 SKU 汇总零成本行、子件成本和不一致订单。它用于判断异常是否只集中在单个组合 SKU；旺店通后台生成 `goodsCost` 的配置根因仍需后台设置或官方规则证据确认。

`audit-reference-cost` 全量验证一个利润月的 `refCostPrice` 覆盖、零值以及与支付日有效成本主数据的逐行一致性。它是变更成本优先级之前的质量门；参考成本为零但没有独立成本主数据时保持待确认，不自动视作真实零成本。

`audit-freight-fallback` 全量盘点仍按收入占比回退的订单，按支付日负责人归属、SKU 毛重及组合件数缺口和运费金额分层。指定订单号时对照原始子件数量、当前组合定义和重量证据。它只读且不改变当前分摊政策；主因统计互斥，缺口统计允许一单多因，输出的高影响订单用于确定人工核查顺序。

商品粒度和 `report.sections.products` 只以商品 ID 为唯一分组键；商品标题、SKU 或历史负责人不参与分组。展示标题优先读取 `master.product_image_mappings` 最近一次导入的权威标题；没有映射时取该商品最近交易日期的订单事实标题。负责人同样使用商品最近交易日期对应的有效归属。查询按商品 ID 从权威映射读取主图；`product_image_url` 是远程 HTTPS 图片链接，不代表图片已下载或嵌入。没有映射时返回空图片，由上层报告明确披露覆盖缺口，不使用订单行或 SKU 组件图片猜测。

`profit actual coverage` 是稳定只读命令：它按支付月、次月15日退款截止和实际运单账单匹配核对数据，但不执行利润计算。`query` 与 `export` 以实时能力清单为准。

运行前必须从实时 `tbcli --help` 与 `tbcli capabilities --json --all` 发现请求分支的命令。请求的命令尚未实现时返回 `CAPABILITY_UNAVAILABLE`；不得使用预估利润、通用仓库查询、原始 SQL或临时脚本冒充。

## 质量门

- 订单头支付金额作为收入总额；归一化后的商品行收入合计必须与订单头一致，并披露归一化前的商品明细权重合计与差额。
- 退款头实际退款金额与退款明细一致，并分别报告精确匹配、无法匹配和多候选。
- 快递账单金额等于目标店铺命中、其他店铺或排除、平台承担、未匹配与调整金额之和。
- 订单物流总额等于商品行物流分摊总额。
- 逐订单验证 `Σ(平台 SKU 单位毛重 × 购买件数)` 与分摊分母一致，`Σ订单-SKU 运费 = 订单运费`，再验证商品、负责人和全店汇总；缺重和组合映射异常逐单披露。
- 推广源金额等于商品归集金额；无正向净销售额时费用仍保留并登记质量问题。
- actual、reference、estimated、explicit_zero、missing 分别统计。
- 负责人加未分配和无法归属利润等于店铺利润。
- 同一组当前事实、主数据和政策版本重复计算结果一致。
- Excel 使用新路径，可打开，表名和中文字段完整，所有汇总与订单商品明细回勾。
